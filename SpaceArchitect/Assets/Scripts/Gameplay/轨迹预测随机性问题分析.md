# 轨迹预测随机性问题分析

## 一、从飞行日志发现的问题

### 1. CoreDeflector 触发时机不一致

**日志观察：**
- 第42帧：速度突然变化 `vel=(15.165,2.089,0.000)`，但**没有** CoreDeflector 记录
- 第43帧：`vel=(15.019,2.442,0.000)`，仍然**没有** CoreDeflector 记录
- 第44帧：才开始记录 `Core[GravityCore]:dist=8.31`

**问题分析：**
- Unity 的 `OnTriggerEnter/OnTriggerStay` 是在**物理更新之后**调用的
- 但飞船可能在**进入 trigger 之前**就已经受到 Core 的 NBody 引力影响
- 这导致预测和实际游戏的行为不一致

### 2. physicsUpdateInterval 导致的不确定性

**代码逻辑：**
```csharp
// CoreDeflector.FixedUpdate()
float lastUpdateTime = shipsInTrigger[shipRoot];
if (Time.unscaledTime - lastUpdateTime < physicsUpdateInterval)
{
    continue; // 跳过这一帧
}
```

**问题：**
- `physicsUpdateInterval` 默认是 `0.02f`（等于 `Time.fixedUnscaledDeltaTime`）
- 但 `Time.unscaledTime` 是**累积时间**，不是对齐到 FixedUpdate 的
- 如果 FixedUpdate 的调用时间与 `physicsUpdateInterval` 不完全对齐，可能导致：
  - 某些帧跳过应用（因为 `Time.unscaledTime - lastUpdateTime < 0.02`）
  - 某些帧重复应用（因为时间差刚好超过 0.02）
- **这会导致每次运行的结果略有不同！**

**示例：**
```
帧1: Time.unscaledTime = 78.1001, lastUpdateTime = 78.1001, 差 = 0.0000 < 0.02 → 应用
帧2: Time.unscaledTime = 78.1201, lastUpdateTime = 78.1001, 差 = 0.0200 = 0.02 → 应用
帧3: Time.unscaledTime = 78.1401, lastUpdateTime = 78.1201, 差 = 0.0200 = 0.02 → 应用
```

但如果 FixedUpdate 的调用时间略有偏差：
```
帧1: Time.unscaledTime = 78.1001, lastUpdateTime = 78.1001, 差 = 0.0000 < 0.02 → 应用
帧2: Time.unscaledTime = 78.1200, lastUpdateTime = 78.1001, 差 = 0.0199 < 0.02 → **跳过！**
帧3: Time.unscaledTime = 78.1401, lastUpdateTime = 78.1001, 差 = 0.0400 > 0.02 → 应用
```

### 3. 多个 CoreDeflector 的处理顺序不确定

**日志观察：**
- 第44-92帧：只有第一个 CoreDeflector (`GravityCore`) 生效
- 第93帧开始：第二个 CoreDeflector (`GravityCore (1)`) 也开始生效
- 但两个 CoreDeflector 的 trigger 可能**重叠**

**问题：**
- Unity 的 `OnTriggerEnter/OnTriggerStay` 的调用顺序是**不确定的**
- 如果两个 CoreDeflector 的 trigger 重叠，Unity 可能：
  - 先调用第一个的 `OnTriggerEnter`
  - 先调用第二个的 `OnTriggerEnter`
  - 或者按 GameObject 的 InstanceID 排序
- **这会导致每次运行的处理顺序不同！**

### 4. 速度缩放的累积误差

**日志观察：**
- `speedMultiplier=1.0010` 很小，但每帧都应用
- 如果每帧都应用 `1.0010`，100帧后累积误差 = `1.0010^100 ≈ 1.105`
- **这会导致长期预测的误差累积！**

## 二、解决方案

### 方案1：修复 physicsUpdateInterval 的应用逻辑

**问题：** 使用 `Time.unscaledTime` 检查间隔会导致不确定性

**解决方案：** 使用**帧计数器**而不是时间差

```csharp
// 在 CoreDeflector 中：
private Dictionary<GameObject, int> shipsInTrigger = new Dictionary<GameObject, int>();
private int fixedUpdateCounter = 0;

void FixedUpdate()
{
    fixedUpdateCounter++;
    int updateInterval = Mathf.RoundToInt(physicsUpdateInterval / Time.fixedUnscaledDeltaTime);
    
    foreach (var ship in shipsInTrigger.Keys)
    {
        int lastUpdateFrame = shipsInTrigger[ship];
        if (fixedUpdateCounter - lastUpdateFrame >= updateInterval)
        {
            // 应用效果
            ApplyGravityAcceleration(ship, shipNBody);
            shipsInTrigger[ship] = fixedUpdateCounter;
        }
    }
}
```

### 方案2：确保 CoreDeflector 触发检测的一致性

**问题：** Unity 的 Trigger 检测时机不确定

**解决方案：** 在预测中也使用**距离检测**，而不是依赖 Trigger 事件

```csharp
// 在 TrajectoryPredictor 中：
// 不要依赖 OnTriggerEnter/OnTriggerStay 的时机
// 而是直接检查距离是否在 trigger 范围内
bool IsInCoreDeflectorRange(Vector3 position, CoreDeflector deflector)
{
    Collider trigger = deflector.GetComponent<Collider>();
    if (trigger == null) return false;
    
    // 使用距离检测（更可靠）
    float dist = Vector3.Distance(position, deflector.transform.position);
    float triggerRadius = GetTriggerRadius(trigger); // 从 bounds 计算
    
    return dist <= triggerRadius;
}
```

### 方案3：固定多个 CoreDeflector 的处理顺序

**问题：** Unity 的 Trigger 调用顺序不确定

**解决方案：** 在预测中，**按固定顺序**处理多个 CoreDeflector（例如按位置排序）

```csharp
// 在 TrajectoryPredictor 中：
// 按 Core 的位置排序，确保处理顺序一致
var sortedDeflectors = cachedSources
    .Where(s => s.hasDeflector)
    .OrderBy(s => s.deflector.corePosition.x)
    .ThenBy(s => s.deflector.corePosition.y)
    .ToList();

foreach (var source in sortedDeflectors)
{
    if (IsInCoreDeflectorRange(currentPos, source))
    {
        // 应用效果
    }
}
```

### 方案4：减少速度缩放的累积误差

**问题：** 每帧都应用速度缩放会导致误差累积

**解决方案：** 在预测中，只在**每个 FixedUpdate 步骤**应用一次速度缩放

```csharp
// 在 TrajectoryPredictor 中：
// 只在 FixedUpdate 间隔时应用速度缩放
if (i % fixedUpdateInterval == 0)
{
    if (speedMultiplier != 1.0f)
    {
        currentVel *= speedMultiplier;
    }
}
```

## 三、推荐的修复优先级

1. **高优先级：修复 physicsUpdateInterval 的应用逻辑**
   - 使用帧计数器而不是时间差
   - 这会导致最大的不确定性

2. **中优先级：确保 CoreDeflector 触发检测的一致性**
   - 使用距离检测而不是依赖 Trigger 事件
   - 这会导致预测和实际游戏的行为不一致

3. **中优先级：固定多个 CoreDeflector 的处理顺序**
   - 按固定顺序处理，避免随机性

4. **低优先级：减少速度缩放的累积误差**
   - 影响较小，但长期预测会有误差
